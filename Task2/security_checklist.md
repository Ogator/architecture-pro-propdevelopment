# Задание 2. Проверочный лист безопасности для бизнес-систем PropDevelopment

## 1. Анализ систем

Источник — диаграмма контейнеров C4 и описание компании. Для каждой системы указано, какие данные она обрабатывает и что важно с точки зрения безопасности.

| Система | Домен | Данные (категория из задания 1) | Особенности с точки зрения безопасности |
| --- | --- | --- | --- |
| Витрина продаж (React) | Продажи | Каталог (публичные), контакты из бронирования (конфиденциальные) | Точка входа клиентов из интернета через firewall. Собственной БД нет, данные получает по REST из client-mart-estate-app, client-mart-app, client-tour-app. Регистрирует клиента одновременно в auth-service-1 и client-crm-app |
| client-mart-estate-app + client-mart-estate-db | Продажи | Объекты недвижимости (публичные/внутренние) | Источник каталога. Сырые данные уходят в DWH через CDC |
| client-mart-app + client-mart-db | Продажи | Сделки, паспортные и финансовые данные покупателей (секретные) | Интеграция с госорганами через СМЭВ (SOAP). Публикует каталог в Kafka. CDC в DWH — секретные данные сделки попадают в общее хранилище |
| client-tour-app + client-tour-db | Продажи | Результаты онлайн-туров (конфиденциальные) | Обменивается данными с client-mart-app |

| auth-service-1 (Keycloak) + auth-db-1 | Продажи | Учётные данные покупателей (секретные) | Регистрация и аутентификация клиентов. Свой реестр учётных записей, не связанный с CRM |
| Витрина сервисов для собственников (iOS/Android) | ЖКУ | ПД собственников, платежи, команды «Умного дома» (секретные) | Точка входа собственников из интернета через firewall. Работает с tenant-core-app (REST, WebSocket) и CRM |
| tenant-core-app + tenant-core-db | ЖКУ | Начисления и оплаты ЖКУ, ремонты (конфиденциальные/внутренние) | Интеграции с поставщиками ЖКУ (УК) и платёжной системой по REST без единых политик безопасности. Получает клиентские данные из CRM. CDC в DWH |
| CRM собственников + crm-tenant-db | ЖКУ | ПД собственников (конфиденциальные) | Третья точка регистрации пользователей. Менеджеры аутентифицируются через AD. CDC в DWH |
| accountant-service-1 + auth-db-1 | Финансы | Финансовый учёт (секретные) | На схеме обозначен как Keycloak, а его БД — как «БД сервиса аутентификации покупателей». Нужно уточнить, нет ли общего хранилища учётных данных с покупательским контуром |
| Active Directory (2 экземпляра) | Финансы / общий | Учётные записи сотрудников (внутренние/секретные) | Два независимых каталога, описания на схеме противоречат связям. Единого реестра учётных записей сотрудников нет |
| Хранилище данных (Greenplum) + DWH (S3) | Дата | Сырые копии всех БД, включая ПД и данные сделок | Ограничений доступа к данным нет. Обезличивания при загрузке через CDC нет. Используется аналитиками BI и бизнес-аналитиками |
| Внешние системы: УК / поставщики ЖКУ, платёжная система, СМЭВ | Партнёры | ПД собственников и клиентов, платежи, данные регистрации | В API партнёров найдены ПД и нарушения изоляции: одна УК видит и меняет данные другой |

### Ключевые наблюдения

1. **Три независимые точки регистрации** пользователей (auth-service-1, client-crm-app, CRM собственников) и два AD без общего реестра. Вероятная причина отображения чужого ФИО в личном кабинете — ошибочное связывание записей между реестрами.
2. **Общее хранилище без разграничения доступа.** CDC переносит в Greenplum сырые данные пяти БД, включая секретные данные сделок, а доступ к ним ничем не ограничен.
3. **Партнёрские API без единых политик.** В них избыточные ПД и нет изоляции данных между УК (уязвимость класса IDOR/BOLA).
4. **Разрыв процесса ИБ.** Специалист по ИБ один на всю компанию и узнаёт не обо всех изменениях.

## 2. Выбор разделов проверочного листа


| Раздел | Решение | Обоснование |
| --- | --- | --- |
| I. Управление доступом | **Включён полностью, высокий приоритет** | Прямо связан с проблемами компании: чужие данные в личном кабинете, партнёр одной УК видит данные другой, нет ограничений доступа в DWH. Несколько реестров учётных записей (Keycloak, два AD, CRM) не позволяют централизованно выдавать и отзывать права |
| II. Безопасность данных | **Включён полностью, высокий приоритет** | Главная проблема компании — нарушен контроль данных. Без классификации, учёта ПД, Data Governance и обезличивания нельзя развивать BI/ML/AI-продукты и выполнять 152-ФЗ |
| III. Защита инфраструктуры | **Включён, средний приоритет** | Firewall на входе есть, но инфраструктура гибридная (свой ЦОД, приватное облако, арендованное облако), и команды временно используют облачные ресурсы на этапах разработки и тестирования. Нужно проверить сегментацию, контроль облака и периметр |
| IV. Управление инцидентами | **Включён, высокий приоритет** | Руководство обеспокоено утечкой у конкурента. При утечке ПД 152-ФЗ обязывает уведомить Роскомнадзор в течение 24 и 72 часов — без мониторинга и плана реагирования это невыполнимо |
| V.1 Общие вопросы (MDM, VPN, облачные бэкапы) | **Включён частично** | Оставлены VPN и облачное резервное копирование — они относятся к гибридной инфраструктуре. Вопросы MDM и неавторизованных устройств касаются корпоративных устройств, о которых данных нет. Мобильное приложение собственников работает на устройствах клиентов, его безопасность вынесена в раздел VI |
| V.2 Оборудование и физическая безопасность | **Исключён** | Проверочный лист посвящён бизнес-системам. Физическая безопасность ЦОД не упоминается среди проблем, данных для её оценки нет. Рекомендуется проверить отдельно в рамках комплексного аудита |
| **VI. Интеграции и API партнёров** (новый) | **Добавлен, высокий приоритет** | Отдельная заявленная проблема компании. Компания планирует развивать сервисы через партнёров, поэтому каждая новая интеграция без единых политик увеличивает риск утечки. Также охватывает интеграции со СМЭВ и платёжной системой и внутренние потоки (Kafka, CDC) |
| **VII. Управление изменениями и соответствие законодательству** (новый) | **Добавлен, высокий приоритет** | Отвечает на две потребности: специалисту по ИБ передают не все решения, и нужно проверить соответствие законодательству РФ (152-ФЗ, требования ФСТЭК, локализация ПД) |

## 3. Проверочный лист

Значения в колонке «Да/нет»:
- **Да / Нет** — ответ следует из схемы или описания;
- **Частично** — мера есть, но не покрывает все системы;
- **Нет данных** — нужно уточнить в ходе аудита, в комментарии сказано, что проверять.

## 4. Итоги и приоритетные меры

По собранным данным самые слабые места — управление доступом, контроль данных и партнёрские интеграции. Первоочередные меры:

1. **Единый реестр пользователей.** Один идентификатор клиента и собственника для всех точек регистрации (Keycloak с федерацией с CRM), объединение или федерация двух AD. Устраняет причину отображения чужих данных в личном кабинете.
2. **Изоляция данных партнёров.** Единый API Gateway, ABAC с атрибутом УК/ЖК, ревью контрактов API на ПД, тестирование на IDOR/BOLA перед подключением партнёра.
3. **Разграничение доступа и обезличивание в DWH.** Ролевая модель доступа в Greenplum, фильтрация полей и псевдонимизация в CDC, отдельные обезличенные витрины для BI/ML.
4. **Data Governance.** Утверждённая политика классификации (на основе задания 1), реестр ПД и ИСПДн, владельцы данных, каталог данных.
5. **Процесс ИБ.** Обязательный security review изменений, security champions в командах, SIEM и план реагирования с учётом сроков уведомления Роскомнадзора.
6. **Уточнить «Нет данных».** Опросить команды эксплуатации и DevOps по разделам III и IV и закрыть оставшиеся пункты в ходе аудита.
