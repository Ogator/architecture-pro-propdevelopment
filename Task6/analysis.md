# Отчёт по результатам анализа Kubernetes Audit Log

**Исходные данные.** Minikube v1.39.0, Kubernetes v1.37.0. Аудит включён политикой `audit-policy.yaml`, журнал пишется в `/var/log/audit.log` API-сервера.

**Объём журнала.** Журнал охватывает 2026-10-04 14:48:01–14:48:44 UTC: 2994 записи, из них 1257 событий на стадии `ResponseComplete`. Скрипт `filter-audit.py` отобрал из них 6 подозрительных событий, они сохранены в `audit-extract.json`.

**Кто выполнял скрипт симуляции.** Все действия скрипта выполнены одной учётной записью:

| Поле | Значение |
| --- | --- |
| Пользователь | `minikube-user` |
| Тип учётной записи | Клиентский сертификат администратора, который minikube записывает в kubeconfig хоста |
| Группы | `system:masters`, `system:authenticated` |
| IP источника | `192.168.49.1` (хост) |
| Клиент | `kubectl/v1.33.1` |
| Время | 14:48:17 UTC, все действия в пределах одной секунды |

## Подозрительные события

1. Доступ к секретам:
   - **Кто:**
     - сначала `minikube-user` от своего имени перечислил secrets в `kube-system` (`list`, код 200);
     - затем тот же пользователь через `--as` выдал себя за сервисный аккаунт `system:serviceaccount:secure-ops:monitoring` и повторил запрос. Получен отказ: код 403, `authorization.k8s.io/decision: forbid`.

     Непосредственно перед этим тот же пользователь проверил права аккаунта через `kubectl auth can-i` с `--as`. В журнале это `selfsubjectaccessreviews`.
   - **Где:** `/api/v1/namespaces/kube-system/secrets`. Запрошен список, а не конкретный секрет. Скрипт искал секрет `default-token-*`, но такие секреты не создаются с Kubernetes 1.24, поэтому `grep` вернул пустую строку, и `kubectl get secret` без имени превратился в `list`. В `kube-system` секретов не оказалось (0 объектов в ответе).
   - **Почему подозрительно:**
     - это разведка: сначала проверка прав чужого аккаунта, затем попытка прочитать все секреты системного namespace от его имени;
     - `kube-system` хранит учётные данные компонентов кластера;
     - имперсонация скрывает действия за чужим именем. Реального инициатора видно только по полю `user`, а не по `impersonatedUser`;
     - сервисному аккаунту мониторинга секреты не нужны вообще.

2. Привилегированные поды:
   - **Кто:** `minikube-user`, 14:48:17.711. Создан под `secure-ops/privileged-pod` (код 201), образ `alpine`, контейнер `pwn` с `securityContext.privileged: true`. Рядом создан `secure-ops/attacker-pod`.
   - **Комментарий:**
     - привилегированный контейнер имеет все capabilities ядра и доступ к устройствам узла. Он может смонтировать файловую систему узла и выйти из контейнера;
     - в Minikube единственный узел является и узлом управления, поэтому такой под даёт доступ к сертификатам кластера в `/var/lib/minikube/certs`, к etcd и к файлу политики аудита;
     - под пропущен потому, что на namespace `secure-ops` нет меток Pod Security. В событии стоит аннотация `pod-security.kubernetes.io/enforce-policy: privileged:latest`, то есть ограничений нет.

3. Использование kubectl exec в чужом поде:
   - **Кто:** `minikube-user`, 14:48:17.809.
   - **Что делал:**
     - открыл сеанс `exec` в системный под `kube-system/coredns-559f6c778d-8c4s8`, контейнер `coredns`;
     - выполняемая команда видна в `requestURI`: `command=cat&command=/etc/resolv.conf`;
     - API-сервер разрешил запрос и установил соединение (код 101 Switching Protocols). Выполнилась ли команда внутри контейнера и что она вывела, в журнале аудита не видно: содержимое сеанса не записывается;
     - сам под принадлежит DNS кластера. `exec` в него позволяет подменить разрешение имён для всех подов.

   **Примечание.** `kubectl` версий 1.30+ открывает `exec` через WebSocket, поэтому в журнале глагол `get`, а не `create`. Проверка из задания `select(.verb=="create" and .objectRef.subresource=="exec")` такое событие не находит. Надёжнее фильтровать только по `objectRef.subresource`.

4. Создание RoleBinding с правами cluster-admin:
   - **Кто:** `minikube-user`, 14:48:17.887. Создан `secure-ops/rolebindings/escalate-binding` (код 201): `roleRef` указывает на ClusterRole `cluster-admin`, субъект — ServiceAccount `secure-ops/monitoring`. Согласования в процессе нет, и никакой механизм его не потребовал.
   - **К чему привело:**
     - `monitoring` получил полные права в namespace `secure-ops`. Проверено: `kubectl auth can-i '*' '*' -n secure-ops --as=system:serviceaccount:secure-ops:monitoring` → `yes`;
     - RoleBinding ограничивает действие роли одним namespace, поэтому секреты `kube-system` аккаунту по-прежнему недоступны (`no`);
     - но в `secure-ops` нет Pod Security, поэтому любой, кто получит токен `monitoring`, сможет создать там привилегированный под и через узел получить весь кластер, как в п. 2;
     - кроме того, аккаунт может сам создавать RoleBinding в `secure-ops` и раздавать права дальше.

5. Удаление audit-policy.yaml:
   - **Кто:** команда `kubectl delete -f /etc/kubernetes/audit-policy.yaml --as=admin` в журнале **не найдена**. Это ожидаемо, и причин две:
     - `kubectl delete -f` читает файл локально, а на хосте такого файла нет. Команда завершилась ошибкой до отправки запроса, и API-сервер её не увидел;
     - политика аудита не является объектом Kubernetes API. Это файл на узле, который API-сервер читает при старте, и удалить его через API нельзя в принципе.

     Попытка выдать себя за пользователя `admin` (`--as=admin`) тоже не дошла до сервера, поэтому её нет в журнале.
   - **Возможные последствия.** Реальная атака на аудит идёт через узел: через привилегированный под из п. 2, `minikube ssh` или доступ к ВМ. Злоумышленник удаляет или ослабляет файл политики либо меняет флаги API-сервера.
     - После перезапуска API-сервер либо перестаёт писать журнал, либо пишет его без нужных событий. Дальнейшие действия становятся невидимы, а расследование — невозможным.
     - В самом журнале это видно только косвенно: по пересозданию зеркального пода `kube-system/kube-apiserver-minikube` пользователем `system:node:minikube` (14:48:02, код 201) и по разрыву во времени между событиями.
     - В этом журнале такое пересоздание соответствует штатному перезапуску minikube с включением аудита (`01-start-minikube-audit.sh`). Фильтр помечает его как `audit-tampering`, потому что сменить политику можно только так.
     - Защита: отправлять журнал за пределы узла (SIEM), контролировать целостность файла политики и флагов API-сервера, оповещать о перезапуске API-сервера.

## Вывод

**Вредоносные действия.** Все пять действий скрипта похожи на атаку:

| Шаг | Цель |
| --- | --- |
| Создание `attacker-pod` и сервисного аккаунта `monitoring` | Плацдарм |
| Разведка прав и чтение секретов от чужого имени | Сбор учётных данных |
| Привилегированный под | Выход на узел |
| `exec` в системный DNS | Вмешательство в работу кластера |
| `cluster-admin` для сервисного аккаунта | Закрепление и повышение прав |
| Попытка удалить политику аудита | Сокрытие следов |

Все действия выполнены за одну секунду одним клиентом, то есть автоматически.

**Компрометация кластера.**
- Кластер следует считать скомпрометированным. В `secure-ops` работает привилегированный под, а это фактически root на единственном узле с control plane. Через него доступны сертификаты кластера, etcd и файл политики аудита.
- `escalate-binding` даёт постоянную точку закрепления: токен `monitoring` с полными правами в namespace, где можно запускать привилегированные поды.
- Сама учётная запись `minikube-user` (сертификат группы `system:masters`) тоже должна считаться скомпрометированной: все действия выполнены ею.
- Нужные меры:
  - удалить `privileged-pod`, `attacker-pod` и `escalate-binding`;
  - пересоздать `monitoring`;
  - перевыпустить CA и сертификаты кластера;
  - проверить узел и файл политики аудита.

**Ошибки политики RBAC:**
1. **Повседневная работа под `system:masters`.** Группа обходит RBAC полностью: ни одна роль её не ограничивает. Сертификат нельзя отозвать до истечения срока. Учётная запись общая, поэтому журнал не показывает, какой человек действовал.
2. **Имперсонация без ограничений.** Администратор может выдать себя за любой сервисный аккаунт или пользователя (`--as`), и все действия попадут в журнал под чужим именем. Право `impersonate` должно выдаваться отдельно, узкой группе и по конкретным именам.
3. **Привязка `cluster-admin` без контроля.** Ничто не мешает создать RoleBinding или ClusterRoleBinding на `cluster-admin`, в том числе для сервисного аккаунта. Нужно ограничивать `bind` по `resourceNames`. Кроме того, admission-политика (ValidatingAdmissionPolicy или Kyverno) должна запрещать привязки к `cluster-admin`, кроме аварийной группы.
4. **Нет Pod Security на новых namespace.** `secure-ops` создан без меток `pod-security.kubernetes.io/enforce`, поэтому привилегированные поды разрешены. Уровень `restricted` нужно задавать по умолчанию: через конфигурацию admission-плагина PodSecurity или политику на создание namespace.
5. **`exec` в `kube-system` доступен обычным администраторам.** Доступ к системным подам нужно оставить только аварийной группе. `pods/exec` выдаётся отдельно от остальных прав на поды.
6. **Сервисные аккаунты с автоматически монтируемым токеном.** `attacker-pod` получил токен `default`. Для аккаунтов, которым API не нужен, следует ставить `automountServiceAccountToken: false`.

**Замечания по самой политике аудита:**
- **Правка группы для RBAC.** В исходной политике `roles` и `rolebindings` указаны в core-группе `""`, где их нет, поэтому создание RoleBinding записывалось бы только на уровне Metadata, без `roleRef`. В использованной политике добавлена группа `rbac.authorization.k8s.io`. Благодаря этому в журнале видно, что выдан именно `cluster-admin`.
- **Секреты в журнале.** Уровень `RequestResponse` для `secrets` записывает в журнал содержимое секретов: журнал сам становится хранилищем секретов. Для `secrets` достаточно уровня `Metadata`. По этой же причине `audit.log` не добавлен в репозиторий, а `audit-extract.json` не содержит тел ответов.
- **Дублирование записей.** Без `omitStages: [RequestReceived]` каждое действие записывается дважды.
